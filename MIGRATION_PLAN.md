# Vue 3 Frontend Migration Plan

## Goal

Migrate `web/` from Nuxt 4 SPA mode to `new-ui/`, which will become a standalone frontend based on:

```text
Vite + Vue 3 + Vue Router + Pinia
+ Nuxt UI v4 standalone + Tailwind CSS 4
```

The existing Nest API, PostgreSQL persistence, shared type package, and Vercel AI SDK UI-message SSE protocol remain unchanged. The existing `web/` application remains the visual and behavioral baseline until the new frontend passes acceptance.

## Architecture Decisions

- Keep `@nuxt/ui` v4 through its official Vite/Vue standalone integration. Nuxt UI is a Vue component library in the target application; Nuxt itself is not installed or run.
- Use `tov-template/` as the reference for directory conventions and developer experience in `new-ui/`: `src/pages`, `src/layouts`, `src/plugins`, file routing, layouts, and automatic plugin installation.
- Keep automatic imports and component imports, but configure them through Nuxt UI's embedded `unplugin-auto-import` and `unplugin-vue-components` instances. Nuxt UI rejects duplicate instances.
- Use Tailwind CSS 4 as the sole utility CSS engine because Nuxt UI requires it. The proof of concept must verify reset behavior, dark mode behavior, and bundle size.
- Use Pinia only for application-shared state that currently uses Nuxt `useState`: session, chat navigation, and selected model. Streaming chat state remains page-local in AI SDK `useChat`.
- Preserve `useApi` as the sole ordinary HTTP boundary. SSE at `POST /api/ai/chat` remains a raw AI SDK UI-message stream and is never wrapped as `R<T>`.

## Compatibility Baseline

The target template currently has a Vite 5 era plugin stack. Nuxt UI 4 standalone is officially tested in its own Vue playground with modern Vite and Vue versions. The target baseline must satisfy Nuxt UI's peer requirements and then verify retained template plugins.

| Dependency | Target |
| --- | --- |
| Node.js | `>= 22.12` |
| pnpm | one current workspace version |
| Vite | current supported release compatible with retained plugins |
| Vue | current Vue 3.5 release |
| Vue Router | `4.5+` initially |
| TypeScript | `5.6+` or 6.x |
| vue-tsc | compatible current release |
| @nuxt/ui | `4.10.0` initially, matching `web/` |
| Tailwind CSS | 4.x |

## Phase 1: Modernize the Template Base

1. Retain the target directory, its Git repository, and source conventions.
2. Update the Vite, Vue, Router, TypeScript, and plugin versions to a compatible combination.
3. Retain and verify these template features:
   - file routes under `src/pages`
   - layouts under `src/layouts`
   - automatic plugins under `src/plugins`
   - Pinia
   - ESLint and Prettier
4. Do not register standalone `unplugin-auto-import` or `unplugin-vue-components` alongside Nuxt UI. Move project directories into Nuxt UI's options instead.
5. Keep the existing template examples during the dependency proof of concept when helpful, then remove them only after the replacement application shell exists.

Acceptance:

- `pnpm dev`, `pnpm typecheck`, and `pnpm build` succeed.
- file routing, layout resolution, and plugin auto-installation continue to work.
- no duplicate auto-import or component-import plugin error occurs.

## Phase 2: Add Nuxt UI Standalone

1. Add `@nuxt/ui/vite` to the Vite plugin list.
2. Register `@nuxt/ui/vue-plugin` with the Vue application.
3. Configure Nuxt UI automatic imports for Vue APIs, Vue Router APIs, and project `src/composables`, `src/stores`, and `src/api` directories.
4. Configure Nuxt UI component scanning for `src/components`.
5. Add Tailwind CSS 4 and the Nuxt UI CSS import.
6. Define the Tailwind CSS and Nuxt UI CSS import order deliberately.
7. Add `isolate` to the `#app` root element.
8. Configure TypeScript declarations and aliases generated by Nuxt UI:
   - `auto-imports.d.ts`
   - `components.d.ts`
   - `#build/ui` aliases
9. Consolidate the legacy Nuxt UI color configuration into Vite's `ui()` options.

Acceptance:

- `UApp`, `useToast`, `useOverlay`, tooltips, dropdowns, modals, and color mode work in Vite.
- Lucide icon names (`i-lucide-*`) resolve.
- Nuxt UI semantic tokens (`bg-default`, `text-muted`, `ring-default`) render correctly.
- Tailwind CSS and Nuxt UI render without obvious reset or dark-mode conflicts.

## Phase 3: Static Visual Proof of Concept

Build a static page without API calls that uses the same Nuxt UI and Tailwind surface as the legacy frontend:

- `UDashboardGroup`, `UDashboardSidebar`, `UDashboardPanel`, `UDashboardNavbar`
- navigation menu, search, dropdown menu, modal, toast, and color mode
- `UChatMessages`, `UChatReasoning`, `UChatShimmer`, `UChatPrompt`, and `UChatPromptSubmit`
- user and assistant messages, reasoning, markdown, syntax-highlighted code, and custom code block controls

Capture desktop, mobile, and dark-mode screenshots under `screenshots/` and compare them with `web/`.

Acceptance:

- structural and interaction parity with the existing homepage and chat shell.
- no visual regression caused by CSS engine order, font loading, icons, root stacking context, or theme configuration.

## Phase 4: Application Shell and Routing

Map the existing routes while retaining the template's conventions:

| Legacy Nuxt source | Target Vue source | Route |
| --- | --- | --- |
| `web/app/pages/index.vue` | `new-ui/src/pages/index.vue` | `/` |
| `web/app/pages/chat/[id].vue` | `new-ui/src/pages/chat/[id].vue` | `/chat/:id` |
| `web/app/layouts/default.vue` | `new-ui/src/layouts/default.vue` | default layout |

Replace Nuxt runtime features:

| Nuxt | Vue/Vite target |
| --- | --- |
| `NuxtPage` / `NuxtLayout` | RouterView and retained layout plugin |
| `navigateTo` | Vue Router push/replace |
| `useRuntimeConfig` | `import.meta.env.VITE_API_BASE_URL` |
| `NUXT_PUBLIC_API_BASE` | `VITE_API_BASE_URL` |
| `useState` | Pinia stores |
| `$fetch` / `createError` | single browser request boundary and typed errors |

## Phase 5: Shared State and API

Create stores for:

- session: server-backed Demo User session, never persisted as authorization state
- chats: server-backed chat navigation list and date grouping, not persisted
- models: selected UI model; persistence is optional and currently unnecessary

Migrate `useApi` while keeping its public behavior:

- normal APIs unwrap `{ code, data, msg }`
- normal API requests disable browser caching
- failures provide readable errors for toast display
- AI chat URL is exposed separately for `DefaultChatTransport`

## Phase 6: Chat Feature Migration

Migrate types, composables/stores, components, and pages in dependency order:

1. shared UI types and API boundary
2. session, chats, and model state
3. navbar, user menu, model selector, rename and confirmation overlays
4. chat title, context usage, indicator, message content, edit form, actions, markdown renderer, and code block
5. homepage chat creation
6. chat detail loading, `useChat`, SSE transport, first-message regeneration, stream completion refresh, voting, editing, regeneration, and stop behavior

Behavior that must not change:

- database history is the model-context source of truth
- a new chat with one user message automatically begins generation
- reasoning parts stream and render
- while streaming, submit/edit/regenerate are guarded and stop remains available
- editing removes the later branch; regeneration replaces the target assistant answer
- title, context use, and sidebar list refresh after stream completion

## Phase 7: Acceptance and Cutover

Run:

```powershell
cd new-ui
pnpm typecheck
pnpm build
```

Browser regression:

1. home UI and color modes
2. Demo User login/logout
3. create chat and automatic first generation
4. streaming text and reasoning
5. stop generation
6. refresh and history restoration
7. follow-up, edit, regenerate, vote, title generation, rename, delete, and search
8. context usage, markdown, code blocks, desktop, and mobile

Only after the new frontend passes these checks should `web/` be archived or removed. Update the root README and HANDOFF document at cutover.
